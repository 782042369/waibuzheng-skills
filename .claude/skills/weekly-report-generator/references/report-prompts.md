## 核心原则

### ⚠️ AI自动术语兜底机制（重要）

Git提交记录中可能包含大量未在术语表中声明的技术词汇，AI必须自动识别并转换。

**判断标准**：如果某个技术词汇多次出现且对理解工作内容有帮助，即使不在术语表中，也应该转换为业务语言。

**自动识别分类**：

| 类别 | 特征关键词 | 转换方向 | 示例 |
|-----|----------|---------|------|
| **前后端** | 端/层/服务/系统 | 业务端表达 | "后端服务"→"系统端" |
| **数据** | 数据/信息/字段/参数 | 数据表达 | "数据接口"→"数据通道" |
| **界面** | 页面/界面/显示/展示 | 界面表达 | "页面组件"→"功能模块" |
| **操作** | 操作/处理/逻辑/流程 | 流程表达 | "操作逻辑"→"操作流程" |
| **加密安全** | 加密/解密/SM4/RSA/AES/Token/JWT/OAuth | 安全保护 | "实现SM4加密"→"提升数据安全性" |
| **认证鉴权** | 认证/鉴权/权限验证 | 权限管理 | "实现Token验证"→"优化权限管理" |
| **缓存压缩** | 缓存/Redis/压缩/gzip | 性能优化 | "实现Redis缓存"→"优化数据访问性能" |
| **验证逻辑** | 正则/验证/校验/格式检查 | 数据准确性 | "支持正则校验"→"完善信息校验" |
| **样式细节** | CSS/样式/列宽/单元格样式 | 界面体验 | "优化CSS选择器"→"优化界面显示效果" |
| **UI交互** | loading/骨架屏/加载动画 | 用户反馈 | "添加loading状态"→"优化数据加载体验" |

## 一、内容提炼标准

### 1. 业务导向

聚焦"完成了什么功能、解决了什么问题、产生了什么价值"，过滤技术实现细节。

### 2. 智能合并

- 同一功能的多次迭代 → 合并为一条
- 相似问题的批量修复 → 归纳为一条
- 关联性强的工作 → 整合描述

### 3. 价值分级

| 优先级 | 类型 | 示例 |
|-------|------|------|
| **高** | 新功能上线、核心流程优化、关键问题修复 | 完善仪表盘统计功能 |
| **中** | 体验改进、性能提升、数据完善 | 优化表格展示效果 |
| **低** | 文档更新、代码整理、临时调试 | （可省略） |

### 4. 数量控制

输出条目控制在 **20-30条** 以内，优先保留高价值工作。

## 二、内容过滤规则

### ❌ 必须过滤的技术细节

**原则**：问自己"领导关心这个吗？"如果答案是否或不确定，就过滤掉。

| 类型 | 过滤内容 | 替换方向 |
|-----|---------|---------|
| **纯组件开发** | "新增Table和Form组件"、"封装公共函数" | 描述业务功能而非组件本身 |
| **底层实现** | 序列化/反序列化、JSON/XML解析 | （直接过滤，纯底层实现） |
| **开发工具** | "添加代码提交检查"、"配置ESLint" | （过滤，除非显著影响交付速度） |
| **代码重构** | "重构数据结构"、"优化类型标注" | 只有带来明显业务价值时才保留 |
| **技术栈升级** | "从Vue2迁移到Vue3" | 改为"优化系统架构，提升运行效率" |
| **依赖升级** | "升级python-docx版本" | 改为"优化文档处理能力" |
| **数据格式** | "geojson数据需要更新"、"JSON格式转换" | （直接过滤，数据格式是技术细节） |
| **数据维护** | "数据定期更新维护"、"数据源同步" | （直接过滤，除非是业务数据质量问题） |

### ✅ 转换为业务语言

| 原始描述（技术细节） | 转换后（业务语言） | 规则参考 |
|-----------------|----------------|---------|
| "实现国密SM4对称加密" | "提升数据安全性和加密保护机制" | 术语表：加密/解密 |
| "优化CSS样式选择器" | "优化界面显示效果和页面视觉体验" | 术语表：CSS/样式 |
| "支持正整数和浮点数校验" | "完善数据录入验证，提升信息准确性" | 术语表：正则/验证 |
| "实现JWT Token认证" | "完善身份验证和访问控制流程" | 术语表：Token/JWT |
| "实现Redis缓存机制" | "优化数据访问性能，提升系统响应速度" | 术语表：缓存/Redis |
| "实现数据压缩功能" | "优化存储空间利用，提升数据传输效率" | 术语表：压缩/gzip |
| "添加表格loading状态" | "优化数据加载交互体验" | 术语表：loading |
| "新增页面加载动画" | "完善页面加载反馈机制" | 术语表：加载动画 |
| "实现骨架屏加载" | "优化数据加载过程反馈" | 术语表：骨架屏 |

### 🔧 构建配置特殊处理

- ❌ "配置ESLint规则"、"设置pre-commit钩子" → 过滤
- ✅ "优化构建配置，显著提升构建性能" → "优化系统构建效率，提升开发速度"

## 四、语言规范

### 1. 表述要求

- 使用动宾结构，动词开头（新增/优化/完善/修复/调整/支持/实现/提升）
- 每条独立成句，不使用连接词
- 避免主观评价，陈述客观事实

### 2. 禁用表达

| 类型 | 禁用示例 |
|-----|---------|
| ❌ 第一人称 | "我/我们完成了..." |
| ❌ 过程描述 | "提交了/修改了/调试了..." |
| ❌ 套话虚词 | "有效地/成功地/进一步/持续推进..." |
| ❌ 总结用语 | "综上所述/总的来说/整体而言..." |

## 五、特殊处理说明

| 类型 | 处理方式 | 示例 |
|-----|---------|------|
| 版本号 | 描述功能升级 | "v1.2.3升级到v1.2.4" → "系统功能升级" |
| 代码量 | 描述实际改进 | "修改了200行代码" → 描述具体功能 |
| 技术栈更换 | 描述业务价值 | "Vue2→Vue3" → "页面架构升级，提升运行效率" |
| 性能指标 | 保留具体数值 | "响应时间从3秒降至1秒" |
| 多人协作 | 统一描述成果 | 不区分个人贡献 |

### ⚠️ 多项目汇总规则

**禁止按项目分组或显示项目名称**：
- ✅ 所有项目的提交记录完全合并，统一编号（1, 2, 3...）
- ❌ 不添加"### XXX项目"分组标题
- ❌ 不在条目中体现"XXX项目中"或"在XXX项目"
- ✅ 所有工作内容统一展示，按业务价值排序

## 六、模板变量填充规则

### 数据结构格式（二维数组对象）

**推荐格式**：使用 `sections` 二维数组对象，每个元素包含 `title` 和 `content` 字段。

```json
{
  "title": "第X周周报（YYYY年MM月DD日 至 YYYY年MM月DD日）",
  "sections": [
    {
      "title": "本周工作情况：",
      "content": "1. 完善项目审核功能...\n2. 优化数据展示效果..."
    },
    {
      "title": "下周工作计划：",
      "content": "1. 继续优化项目管理功能...\n2. 推进测试和上线工作..."
    },
    {
      "title": "需协调解决问题：",
      "content": "暂无"
    }
  ]
}
```

**优点**：
- ✅ 章节名称灵活，不受模板限制
- ✅ 可以自由增减章节
- ✅ 更符合实际 Word 模板的结构

### AI 填充指南

#### 1. 从模板结构中提取章节

运行 `orchestrate_reports.py` 后会生成 `template_structure.json`，其中包含模板的章节结构：

```json
{
  "structure": {
    "sections": [
      {"title": "本周工作情况：", "level": 2},
      {"title": "下周工作计划：", "level": 2},
      {"title": "需协调解决问题：", "level": 2}
    ]
  }
}
```

#### 2. 根据章节类型填充内容

| 章节标题模式 | 填充内容 | 推导规则 |
|------------|---------|---------|
| `*工作*`、`*完成*`、`*本周*` | 清洗后的工作内容 | 使用 Git 日志清洗结果 |
| `*计划*`、`*下周*`、`*安排*` | 下周工作计划 | 基于本周工作推导 |
| `*总结*`、`*汇总*` | 本周工作总结 | 提炼关键进展（3-5条） |
| `*问题*`、`*风险*`、`*协调*` | 问题和风险 | 识别技术问题和业务风险 |
| `*日期*`、`*时间*`、`*周期*` | 时间范围 | 使用"YYYY年MM月DD日"格式 |
| `*标题*`、`*项目*` | 周报标题 | 使用"第X周周报（时间范围）" |

#### 3. 各章节填充规则

**工作内容章节**（如"本周工作情况"、"完成情况"）：
- 使用清洗后的工作内容
- 遵循内容提炼标准
- 按业务价值排序
- 控制在 20-30 条

**计划章节**（如"下周工作计划"、"工作安排"）：
- 基于本周工作推导
- 推导原则：
  - 本周有优化/完善 → 下周继续优化
  - 本周有新功能开发 → 下周进行测试/上线
  - 本周有修复工作 → 下周进行验证/监控
  - 本周有数据完善 → 下周进行数据分析/应用

**总结章节**（如"本周总结"、"工作总结"）：
- 总结本周工作成果
- 提炼关键进展
- 控制在 3-5 条

**问题和风险章节**（如"问题"、"风险"、"需协调解决问题"）：
- 识别技术问题和业务风险
- 提出应对建议
- 如果没有明显风险，填写"暂无"

⚠️ **必须过滤的问题类型**（重要）：
- ❌ 数据格式相关："geojson数据需要更新维护"、"JSON格式转换问题"（纯技术细节）
- ❌ 数据维护相关："数据定期更新维护"、"数据源同步问题"（运维细节，非业务问题）
- ❌ 技术实现细节："组件API兼容性"、"框架版本升级"（开发层面问题）
- ✅ 保留的业务问题：数据准确性问题、功能缺失、用户体验问题、性能影响业务的问题

### 填充质量检查

1. **完整性**：所有模板章节是否都已填充
2. **一致性**：风格、术语、格式是否统一
3. **准确性**：日期、内容、补充内容是否合理
4. **可读性**：语言是否流畅，结构是否清晰
