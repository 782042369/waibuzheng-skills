# 周报生成器

从Git提交记录自动生成专业的工作周报文档。

## 快速开始

生成周报需要 **5 个步骤**：

```
收集输入 → 解析时间 → 获取日志 → 清洗内容 → 导出文件
```

**需要收集的信息**：
- ✅ **项目路径**（支持多项目）
- ✅ **时间范围**（支持"本周"、"上周"、自定义日期）
- ✅ **模板文件**（可选，推荐提供）
- ✅ **输出路径和文件名**

## 工作准则

- ✅ **完整执行**：必须完成全部 5 个步骤，不能中途停止
- ✅ **进度可见**：每个步骤打印 `📍 Step X: [名称]`
- ⚠️  **只读 Git 日志**：禁止读取项目源代码文件（保护隐私）
- ⚠️  **精简模式默认**：脚本默认使用精简模式，减少 token 消耗

## ⚠️ 关键警告（多周处理时必须遵守）

🚨 **禁止跳过内容清洗**：

**绝对禁止的行为**：
- ❌ 直接输出 Git 的原始提交信息
- ❌ 使用技术术语（API、接口、组件、数据库等）
- ❌ 跳过 Step 4 的内容清洗步骤
- ❌ 在多周处理时降低质量标准

**必须执行的要求**：
- ✅ 每周都必须执行完整的内容清洗（Step 4）
- ✅ 将技术术语转换为业务语言
- ✅ 同类工作合并，避免碎片化
- ✅ 打印进度确认清洗已完成

**多周处理检查点**：
- 每完成一周，打印：`✅ 第 X 周周报已生成（已清洗内容）`
- 如果发现某周未清洗，立即停止并报告错误

**详细工作流程**：见 [references/workflow.md](references/workflow.md)

## 工作流程（5 步）

### Step 1: 收集用户输入

需要收集以下信息：

1. **项目路径**（必需）
   - 单个：`/Users/yanghongxuan/yunji/huadian/ecm-ui`
   - 多个：`/path/to/proj1, /path/to/proj2, /path/to/proj3`

2. **时间范围**（必需）
   - 相对时间：`本周`、`上周`、`本月`
   - 绝对时间：`2025.1.10 - 2025.1.15`
   - 混合时间：`上周三到今天`

3. **示例周报**（可选，推荐）
   - 方式1：直接粘贴文本内容
   - 方式2：提供模板文件路径（.md 或 .docx）

4. **输出方式**（必需）
   - **按天分类**：按周一到周五分组展示
   - **合并输出**：任务凝练合并，统一编号

5. **输出路径和文件名**（必需）
   - 输出路径：`/path/to/output`
   - 文件名：`20250115周报.md` 或 `20250115周报.docx`

6. **命名规则**（可选，多周时推荐）
   - 默认规则：`周报YYYYMMDD-YYYYMMDD.md`
   - 自定义规则：支持占位符 `{N}`（周序号）、`{START}`（起始日期）、`{END}`（结束日期）
   - 示例：`项目第{N}周周报.docx` → `项目第1周周报.docx`

**详细步骤说明**：见 [references/workflow.md#step-1-收集用户输入](references/workflow.md#step-1-收集用户输入)

### Step 2: 解析时间并确认

AI 解析时间表达式，计算对应的日期范围：

**解析规则**：
- 相对时间对齐到工作周（周一至周五）
- 绝对时间保持原样
- 混合时间计算实际日期范围

**示例**：
- `本周` → 2025年1月13日（周一）至2025年1月17日（周五）
- `上周` → 2025年1月6日（周一）至2025年1月10日（周五）

**交互确认**：
```
AI: "本周 = 2025年1月13日（周一）至2025年1月17日（周五），确认吗？"
用户: "确认" 或 "调整日期"
```

### Step 1.5: 检测时间跨度并拆分（多周情况）

**判断标准**：
- 时间跨度 ≤ 7 天：按单周处理
- 时间跨度 > 7 天：需要按周拆分

**示例**：
```
用户输入：2025-5-12 到 2025-5-25

AI 计算：
时间跨度：14天（2周）
- 第1周：2025-05-12（周一）至 2025-05-18（周日）
- 第2周：2025-05-19（周一）至 2025-05-25（周日）

AI 确认：
检测到时间跨度为 2 周，将生成 2 个周报文件：
1. 项目第一周周报（2025-05-12 至 2025-05-18）
2. 项目第二周周报（2025-05-19 至 2025-05-25）

确认吗？
```

**详细的多周处理指南**：见 [references/multi-week-guide.md](references/multi-week-guide.md)

### Step 3: 获取Git日志

⚠️ **重要限制**：
- 🔒 **只读取 Git 日志**：AI 只能通过 `get_git_logs.py` 获取项目的提交记录
- 🚫 **禁止读取项目文件**：AI 绝对不能使用 Read、Glob、Grep 等工具读取项目内容
- 🚫 **禁止探索项目结构**：AI 不能探索项目的目录结构、源代码、配置文件等
- 📊 **只基于提交信息**：AI 只基于 Git 提交的 message 来生成周报内容

**调用方式**：

```bash
# 默认调用（精简模式，推荐）
python3 ~/.claude/skills/weekly-report-generator/get_git_logs.py \
  --paths "项目路径1,项目路径2" \
  --since "2025-01-13" \
  --until "2025-01-17"

# 如需完整模式（包含 hash、author、email 等字段），添加 --no-minimal
python3 ~/.claude/skills/weekly-report-generator/get_git_logs.py \
  --paths "项目路径1,项目路径2" \
  --since "2025-01-13" \
  --until "2025-01-17" \
  --no-minimal
```

**精简模式（默认）优势**：
- ✅ 减少 **约 60%** token 消耗
- ✅ 保留所有必要信息（提交内容、日期、星期）
- ✅ 不影响后续的内容清洗和周报生成

**详细说明**：见 [references/workflow.md#step-3-获取git日志脚本1](references/workflow.md#step-3-获取git日志脚本1)

### Step 3.5: 分析示例模板（如果用户提供）

**条件触发**：用户在 Step 1 中提供了示例周报文件路径

**调用脚本**：
```bash
python3 ~/.claude/skills/weekly-report-generator/analyze_template.py \
  --template "示例周报.docx" \
  --output template_structure.json
```

**返回数据**（JSON）：
```json
{
  "type": "word",
  "structure": {
    "title": "A公司集团工程部技术服务项目",
    "sections": [...]
  },
  "variables": {
    "{{起始日期}}": {...},
    "{{结束日期}}": {...},
    "{{本周工作情况}}": {...}
  }
}
```

**支持的功能**：
- ✅ 自动检测文件类型（.md / .docx）
- ✅ 提取标题层级结构
- ✅ 识别变量占位符（`{{变量名}}`）
- ✅ 返回完整的原始内容

**详细说明**：见 [references/workflow.md#step-35-分析示例模板如果用户提供](references/workflow.md#step-35-分析示例模板如果用户提供)

### Step 4: 清洗内容 + 格式化

🚨 **严重警告**：AI 必须执行内容清洗，不能直接输出原始 Git 提交信息！

**这是最重要的一步**：
- ⚠️ 跳过此步骤是严重错误，会导致周报质量不合格
- ⚠️ 即使在多周批处理时，每周都必须执行清洗
- ⚠️ 不能因为"时间紧"或"token 限制"而跳过清洗
- ⚠️ 这是不可妥协的质量要求

**禁止行为**：
- ❌ 直接输出 Git 的原始提交信息
- ❌ 使用技术术语（API、接口、组件、数据库等）
- ❌ 罗列代码细节和技术实现
- ❌ 跳过内容清洗步骤

**必须执行**：
- ✅ 必须基于 `report-prompts.md` 的规则清洗内容
- ✅ 将技术术语转换为业务语言
- ✅ 同类工作合并，避免碎片化
- ✅ 使用正式的汇报语言

**进度打印（必须）**：
```
📍 Step 4: AI 清洗内容 + 格式化
⏳ 正在清洗 Git 提交信息...
✅ 内容清洗完成（提炼了 X 条工作内容）
⏳ 正在按照模板格式化...
✅ 格式化完成
```

**清洗示例**：

输入（Git提交信息）：
```
- 修复仪表盘数据统计错误
- 仪表盘新增项目个数字段
- 表格组件支持提示文本颜色配置
```

输出（清洗后）：
```markdown
1. 完善仪表盘统计功能，新增项目数量展示，修复数据统计异常问题
2. 优化表格展示效果，支持提示文本颜色自定义配置
```

**输出方式**：

**方式1：按天分类**
```markdown
## 本期工作内容

### 周一
1. 完善仪表盘统计功能，新增项目数量展示
### 周二
2. 优化表格展示效果
```

**方式2：合并输出**
```markdown
## 本期工作内容

1. 完善仪表盘统计功能，新增项目数量展示
2. 优化表格展示效果
```

**详细清洗规则**：见 [references/content-rules.md](references/content-rules.md)

### Step 5: 导出文件

调用 `export_report.py` 生成文件：

```bash
# Markdown 输出（.md 扩展名）
python3 ~/.claude/skills/weekly-report-generator/export_report.py \
  --content "清洗后的周报内容" \
  --output "输出路径" \
  --filename "周报.md"

# Word 输出（.docx 扩展名）
python3 ~/.claude/skills/weekly-report-generator/export_report.py \
  --content "清洗后的周报内容" \
  --output "输出路径" \
  --filename "周报.docx"

# 自动文件名（默认 Markdown 格式）
python3 ~/.claude/skills/weekly-report-generator/export_report.py \
  --content "清洗后的周报内容" \
  --output "输出路径" \
  --start-date "2025-01-13" \
  --end-date "2025-01-17"
```

**自动格式检测**：
- **根据 `filename` 扩展名自动检测输出格式**：
  - `.md` → Markdown 格式
  - `.docx` → Word 格式
  - 无扩展名或默认 → Markdown 格式
- **无需手动指定格式**：脚本根据文件名自动选择输出方式

**详细说明**：见 [references/workflow.md#step-5-导出文件脚本2](references/workflow.md#step-5-导出文件脚本2)

### Step 6: 多周循环处理（如果时间跨度 > 7 天）

🚨 **多周处理警告**：

**必须遵守的规则**：
- ✅ 每周都必须执行完整的 5 个步骤（包括 Step 4 清洗）
- ✅ 不能因为批处理而降低质量标准
- ✅ 每周生成后都要检查是否已完成清洗
- ✅ 每周都打印进度确认

**循环流程**：
```
for 每周 in 时间范围:
  1. 调用 get_git_logs.py 获取该周的日志（默认精简模式）
  2. 调用 analyze_template.py 分析模板（仅第一次）
  3. 🚨 **必须执行**：AI 清洗内容（转换术语、合并同类项）
  4. 调用 export_report.py 导出文件
  5. ✅ 确认并打印：第 X 周周报已生成（已清洗内容）
```

**常见错误**：
- ❌ 直接使用 Git 原始提交信息（未清洗）
- ❌ 使用技术术语（API、接口、组件等）
- ❌ 跳过清洗步骤，直接导出

**错误处理**：
- 如果发现某周未清洗，立即停止处理
- 报告错误：第 X 周未执行内容清洗
- 重新生成该周周报

**示例输出**：
```

⏳ 正在调用脚本：get_git_logs.py

⏳ 正在调用脚本：get_git_logs.py
✅ Git 日志获取完成（共 X 条提交记录）
⏳ 正在清洗 Git 提交信息...
✅ 内容清洗完成（提炼了 X 条工作内容）
⏳ 正在调用脚本：export_report.py
✅ 已生成：项目第二周周报.docx（已清洗内容）
```

## 核心功能

- **灵活时间解析**：支持"本周"、"上周"、"2025.1.10-2025.1.15"等多种时间表达
- **智能内容清洗**：将技术术语转换为业务语言，去除专业名词
- **两种输出方式**：按天分类（周一到周五）或合并输出（凝练任务）
- **多项目支持**：汇总多个项目的提交记录
- **自定义风格**：基于用户提供的示例周报模仿生成

## 依赖安装

使用前需要安装 Python 依赖：

```bash
pip install gitpython python-docx
```

或使用 requirements.txt：

```bash
pip install -r requirements.txt
```

**依赖清单**：
- `gitpython>=3.1.40` - Git操作
- `python-docx>=0.8.11` - Word文件读写（可选，仅Word输出时需要）

**注意**：
- Markdown 输出无需额外依赖（推荐）
- Word 输出需要安装 `python-docx`
- 如遇到 Python 版本问题，使用 `python3.12` 运行脚本

## 注意事项

1. **时间格式**：脚本使用 YYYY-MM-DD 格式（如 2025-01-13）
2. **路径格式**：支持 Windows 和 Unix 路径，推荐使用绝对路径
3. **非Git目录**：如果路径不是 Git 仓库，脚本会跳过并提示
4. **周末提交**：脚本会自动过滤周末的提交，只保留周一到周五
5. **术语转换**：AI 会严格遵循术语转换表格，将技术名词转换为业务语言
6. **示例风格**：如果提供了示例周报，AI 必须严格模仿，不使用默认模板
7. **自动格式检测**：
   - 脚本根据 `filename` 扩展名自动检测输出格式
   - `.md` → Markdown，`.docx` → Word
   - 无需手动指定格式参数
8. **Word 输出**：需要安装 `python-docx`，建议使用 `python3.12` 运行
9. **多周批处理**（20-50 周）：
   - AI 会自动检测时间跨度并按周拆分
   - 推荐"先预览第 1 周，确认后批量生成"方式
   - AI 会显示进度条和预计剩余时间
   - 🚨 **重要**：每周都必须执行完整的内容清洗，不能跳过
   - 🚨 **重要**：每完成一周都要打印"已清洗内容"确认标记
   - 🚨 **重要**：如果发现某周未清洗，立即停止并报告错误
   - 如果某周生成失败，AI 会记录错误但继续处理其他周
10. **命名规则**：
    - 支持自定义命名规则，使用占位符 `{N}`、`{START}`、`{END}`
    - 示例：`项目第{N}周周报.docx` → `项目第1周周报.docx`
    - 多周时必须提供命名规则
11. **Token 优化**（重要）：
    - ✅ **精简模式默认启用**：脚本默认使用精简模式，减少约 60% token 消耗
    - ✅ AI 只通过 `get_git_logs.py` 获取 Git 日志，不读取项目文件
    - 🚫 **禁止读取项目文件**：AI 不能使用 Read、Glob、Grep 等工具读取项目内容
    - 🚫 **禁止探索项目结构**：AI 不能探索项目的目录结构、源代码、配置文件等
    - 📊 **只基于提交信息工作**：AI 只基于 Git 提交的 message 来生成周报
    - 原因：
      - 🎯 减少 token 消耗（避免读取大量不必要的项目文件）
      - 🔒 保护项目隐私（不读取项目的源代码和敏感信息）
      - ⚡ 提高处理速度（只处理必要的 Git 日志数据）
      - 📊 专注工作内容（只基于提交记录生成工作汇报）
