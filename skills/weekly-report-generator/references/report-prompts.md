
## 处理规则

### ⚠️ AI自动术语分析兜底机制

**重要**：Git提交记录中可能包含大量未在术语表中声明的技术词汇。AI必须自动识别并转换这些术语，不能因为没有在术语表中就跳过。

**AI自动术语分析原则**：
1. **前后端术语自动识别**：
   - 包含"端"、"层"、"服务"、"系统"的技术词 → 转为业务表达
   - 例如："后端服务" → "系统端"、"前端组件" → "界面功能模块"

2. **数据相关术语自动识别**：
   - 包含"数据"、"信息"、"字段"、"参数"的技术词 → 转为业务表达
   - 例如："数据接口" → "数据通道"、"字段校验" → "信息验证"

3. **界面相关术语自动识别**：
   - 包含"页面"、"界面"、"显示"、"展示"的技术词 → 转为业务表达
   - 例如："页面组件" → "页面功能模块"、"界面渲染" → "界面显示"

4. **操作相关术语自动识别**：
   - 包含"操作"、"处理"、"逻辑"、"流程"的技术词 → 转为业务表达
   - 例如："操作逻辑" → "操作流程"、"处理流程" → "处理方式"

5. **纯技术实现自动识别（新增，严格执行）**：
   - **加密/安全相关**：包含"加密"、"解密"、"SM4"、"RSA"、"AES"、"MD5"、"SHA"、"Token"、"JWT"、"OAuth"、"认证"、"鉴权" → **直接过滤**
   - **数据格式相关**：包含"序列化"、"反序列化"、"JSON解析"、"XML解析" → **直接过滤**
   - **缓存相关**：包含"实现缓存"、"Redis缓存"、"内存缓存" → **直接过滤**
   - **压缩相关**：包含"实现压缩"、"数据压缩"、"文件压缩"、"gzip" → **直接过滤**
   - **验证逻辑**：包含"正则"、"字符串验证"、"格式验证"、"类型检查"、"支持.*校验"、"支持.*验证"、"支持.*校验" → **直接过滤**
   - **样式细节**：包含"CSS样式"、"样式选择器"、"列宽"、"单元格样式" → **直接过滤**

**AI判断标准**：如果看到某个技术词汇多次出现且对理解工作内容有帮助，即使不在术语表中，也应该转换为业务语言。目标是让领导能够理解，而不是精确映射术语表。

### 一、内容提炼标准
1. **业务导向**：聚焦"完成了什么功能、解决了什么问题、产生了什么价值"，过滤技术实现细节
2. **智能合并**：
   - 同一功能的多次迭代合并为一条
   - 相似问题的批量修复归纳为一条
   - 关联性强的工作整合描述
3. **价值分级**：
   - 高优先级：新功能上线、核心流程优化、关键问题修复
   - 中优先级：体验改进、性能提升、数据完善
   - 低优先级：文档更新、代码整理、临时调试（可省略）
4. **数量控制**：输出条目控制在20-30条内以内，优先保留高价值工作

### ⚠️ 内容过滤规则（新增）
**以下类型的技术实现细节必须过滤掉，不要出现在周报中**：

1. **纯技术组件/库的开发**（过滤）：
   - ❌ "新增Table和Form组件"
   - ❌ "封装公共函数方法"
   - ❌ "重构表格编辑器组件"
   - ✅ 改为：如果该组件是业务功能的一部分，描述业务功能而非组件本身

2. **底层技术实现细节**（过滤）：
   - ❌ "实现国密SM4对称加密" / "实现SM4加密" / "国密加密"
   - ❌ "实现RSA非对称加密" / "实现AES加密" / "实现MD5/SHA加密"
   - ❌ "优化CSS样式选择器" / "调整CSS样式"
   - ❌ "改进字符串验证逻辑" / "优化正则表达式"
   - ❌ "支持正整数和浮点数校验" / "实现数据类型验证" / "添加数据格式校验"
   - ❌ "调整表格列宽设置" / "修改单元格样式"
   - ❌ "实现Token验证" / "实现JWT认证" / "实现OAuth登录"
   - ❌ "实现数据序列化" / "实现JSON解析"
   - ❌ "实现缓存机制" / "实现Redis缓存"
   - ❌ "实现数据压缩" / "实现文件压缩"
   - ✅ 改为：描述业务价值，如"提升数据安全性"、"优化界面显示效果"

3. **开发工具和流程相关**（过滤）：
   - ❌ "添加代码提交检查"
   - ❌ "配置ESLint规则"
   - ❌ "设置pre-commit钩子"
   - ❌ "优化构建配置"
   - ✅ 这些都不应该出现在周报中

4. **代码重构和优化**（谨慎保留）：
   - ❌ "重构进度相关数据结构"
   - ❌ "优化代码类型标注"
   - ❌ "清理冗余代码"
   - ✅ 只有当重构带来明显的业务价值时才保留，如"优化系统性能，提升响应速度"

5. **技术栈更换和升级**（改为业务价值）：
   - ❌ "从Vue2迁移到Vue3"
   - ❌ "升级python-docx版本"
   - ✅ 改为："优化系统架构，提升运行效率"

**判断标准**：问自己"这个工作内容对领导有价值吗？领导关心吗？"如果答案是"否"或"不确定"，就过滤掉。

### 二、语言规范
1. **表述要求**：
   - 使用动宾结构，动词开头（新增/优化/完善/修复/调整/支持/实现/提升）
   - 每条独立成句，不使用连接词
   - 避免主观评价，陈述客观事实

2. **禁用表达**：
   - ❌ 第一人称：我/我们完成了...
   - ❌ 过程描述：提交了/修改了/调试了...
   - ❌ 套话虚词：有效地/成功地/进一步/持续推进...
   - ❌ 总结用语：综上所述/总的来说/整体而言...

4. **性能指标**：保留具体数值，如"响应时间从3秒降至1秒"
5. **多人协作**：不区分个人贡献，统一描述团队成果
6. **多项目汇总**：❌ 禁止按项目分组或显示项目名称

   - 不添加"### XXX项目"这样的分组标题
   - 不在条目中体现"XXX项目中"或"在XXX项目"
   - 所有工作内容统一展示，按业务价值排序

## 模板变量填充规则

当使用自定义模板时，AI需要根据template_structure.json中的变量定义，智能填充不同类型的变量。

### 变量类型识别

AI需要根据变量名称自动识别变量类型：

| 变量类型 | 常见变量名示例 | 说明 |
|---------|--------------|------|
| `date` | 起始日期、结束日期、汇报周期、时间范围 | 日期相关变量 |
| `content` | 本周工作、本周工作情况、本周工作内容、完成情况 | 本周工作内容 |
| `future_plan` | 下周计划、下周工作计划、工作安排 | 下周计划内容 |
| `summary` | 本周总结、工作总结、总结 | 本周总结内容 |
| `risk` | 问题、风险、存在问题、问题和风险、风险点 | 问题和风险内容 |
| `title` | 标题、项目名称 | 文档标题 |

### 各类型变量填充规则

#### 1. date类型变量

**填充规则**：
- 使用start_date和end_date
- 格式化为"YYYY年MM月DD日"或"YYYY.MM.DD"
- 如果变量名包含"周期"，使用"YYYY年MM月DD日（周一）至YYYY年MM月DD日（周五）"

**示例**：
```
{{起始日期}} → 2025年01月13日
{{结束日期}} → 2025年01月17日
{{汇报周期}} → 2025年01月13日（周一）至2025年01月17日（周五）
```

#### 2. content类型变量

**填充规则**：
- 使用清洗后的工作内容
- 遵循内容提炼标准
- 使用动宾结构，动词开头
- 按业务价值排序

**示例**：
```
{{本周工作情况}} →
1. 完善仪表盘统计功能，新增项目数量展示，修复数据统计及图表显示异常问题
2. 优化表格展示效果，支持提示文本颜色自定义配置
3. 扩展合同管理模块，增加企业信用代码信息项
...
```

#### 3. future_plan类型变量

**填充规则**：
- 基于本周工作内容推导
- 识别未完成的工作项
- 推断可能的后续任务
- 保持与content相同的风格
- 如果无法推导，留空或标记"待定"

**推导原则**：
1. **本周有优化/完善工作** → 下周继续优化（如"继续优化..."）
2. **本周有新功能开发** → 下周进行测试/上线（如"推进...测试和上线工作"）
3. **本周有修复工作** → 下周进行验证/监控（如"验证...修复效果"）
4. **本周有数据完善** → 下周进行数据分析/应用（如"基于...数据进行分析"）

**示例**：
```
{{下周工作计划}} →
1. 继续优化仪表盘性能，提升大数据量下的加载速度
2. 完善表格导出功能，支持Excel格式导出
3. 推进合同管理模块的测试和上线工作
```

#### 4. summary类型变量

**填充规则**：
- 总结本周工作成果
- 提炼关键进展
- 评估整体完成情况
- 使用正式、简洁的语言
- 控制在3-5条

**示例**：
```
{{本周总结}} →
1. 本周主要完成了仪表盘功能优化和合同管理模块扩展，系统功能得到进一步提升
2. 解决了多个数据统计和图表显示问题，用户体验得到明显改善
3. 为下周的性能优化和功能上线奠定了基础
```

#### 5. risk类型变量

**填充规则**：
- 识别本周遇到的技术问题
- 评估潜在的业务风险
- 提出风险应对建议
- 只列出真实存在的风险，不虚构
- 如果没有明显风险，留空或填写"暂无"

**风险类型**：
1. **性能风险**：如"大数据量情况下性能有待优化"
2. **兼容性风险**：如"部分老旧浏览器兼容性问题需要进一步测试"
3. **数据风险**：如"部分历史数据质量需要进一步核实"
4. **进度风险**：如"部分功能开发进度略有延迟，需要加快节奏"

**示例**：
```
{{存在问题和风险}} →
1. 仪表盘在大数据量情况下性能有待优化，下周将继续进行性能调优
2. 部分老旧浏览器兼容性问题需要进一步测试和验证
3. 合同管理模块的数据导入功能需要与业务部门进一步确认需求
```

#### 6. title类型变量

**填充规则**：
- 如果模板structure.title存在，使用模板标题
- 如果用户提供了项目名称，使用项目名称
- 否则，使用"工作周报"或"周工作报告"

**示例**：
```
{{标题}} → A公司集团工程部技术服务项目
```

### 模板变量填充流程

**AI填充模板时的完整流程**：

1. **读取template_structure.variables**：
   - 识别所有变量及其类型
   - 确定哪些变量是必需的

2. **按类型填充变量**：
   - date类型：直接使用日期
   - content类型：使用清洗后的工作内容
   - future_plan类型：基于content推导
   - summary类型：基于content总结
   - risk类型：基于content识别
   - title类型：使用模板标题或默认标题

3. **验证必需变量**：
   - 检查所有required=true的变量是否已填充
   - 如果有缺失，尝试补充或标记为"待定"

4. **生成最终内容**：
   - 按照structure.sections组织内容
   - 使用章节标题
   - 保持层级结构
   - 生成Markdown格式文本

### 特殊情况处理

1. **模板变量为空**：
   - 如果required=true，尝试补充内容
   - 如果required=false，可以留空

2. **变量无法识别类型**：
   - 根据变量名称推断
   - 如果无法推断，当作content类型处理

3. **多个相似变量**：
   - 如同时存在"本周工作"和"本周工作情况"
   - 合并为同一个内容，避免重复

4. **变量名称不规范**：
   - 如"work_content"或"this_week"
   - 根据上下文推断类型
   - 优先按content类型处理

### 填充质量检查

**AI填充完成后，需要进行质量检查**：

1. **完整性检查**：
   - 所有required变量是否已填充
   - 内容是否完整，不中断

2. **一致性检查**：
   - 风格是否统一
   - 术语是否一致
   - 格式是否规范

3. **准确性检查**：
   - 日期是否正确
   - 内容是否基于实际工作
   - 补充内容是否合理

4. **可读性检查**：
   - 语言是否流畅
   - 结构是否清晰
   - 是否易于理解

**如果不通过检查，AI需要重新调整内容。**
