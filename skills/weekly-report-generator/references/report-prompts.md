
## 处理规则

### 一、内容提炼标准
1. **业务导向**：聚焦"完成了什么功能、解决了什么问题、产生了什么价值"，过滤技术实现细节
2. **智能合并**：
   - 同一功能的多次迭代合并为一条
   - 相似问题的批量修复归纳为一条
   - 关联性强的工作整合描述
3. **价值分级**：
   - 高优先级：新功能上线、核心流程优化、关键问题修复
   - 中优先级：体验改进、性能提升、数据完善
   - 低优先级：文档更新、代码整理、临时调试（可省略）
4. **数量控制**：输出条目控制在20条以内，优先保留高价值工作

### 二、语言规范
1. **表述要求**：
   - 使用动宾结构，动词开头（新增/优化/完善/修复/调整/支持/实现/提升）
   - 每条独立成句，不使用连接词
   - 避免主观评价，陈述客观事实

2. **禁用表达**：
   - ❌ 第一人称：我/我们完成了...
   - ❌ 过程描述：提交了/修改了/调试了...
   - ❌ 套话虚词：有效地/成功地/进一步/持续推进...
   - ❌ 总结用语：综上所述/总的来说/整体而言...

### 三、术语转换映射表

| 技术术语 | 业务表达 |
|---------|---------|
| API/接口/RESTful | 数据通道/数据对接/系统连接 |
| 前端/客户端/UI | 页面端/用户界面/操作界面 |
| 后端/服务端/Server | 系统端/服务层/处理中心 |
| 组件/控件/Widget | 功能模块/页面元素/操作单元 |
| 字段/参数/属性 | 信息项/数据项/配置项 |
| 数据库/数据表/Schema | 数据存储/数据记录/信息库 |
| 缓存/Redis/Memory | 快速存储/临时存储/数据缓冲 |
| 请求/响应/返回值 | 数据交互/系统反馈/处理结果 |
| Bug/Issue/缺陷 | 问题/异常/故障 |
| 重构/封装/抽象 | 结构优化/逻辑整理/功能梳理 |
| CSS/样式/渲染 | 显示效果/界面展示/视觉呈现 |
| 部署/发布/上线 | 系统更新/功能发布/正式启用 |
| 联调/集成/对接 | 系统协同/功能整合/对接测试 |
| JSON/XML/序列化 | 数据格式/结构化数据 |
| Token/Session/Cookie | 身份凭证/会话信息/访问标识 |
| 权限/鉴权/认证 | 权限管理/访问控制/身份验证 |
| 异步/同步/并发 | (转为业务效果描述) |
| Git/分支/Commit | (不体现版本控制过程) |
| 框架/库/依赖 | (转为具体功能描述) |

### 四、特殊处理说明

1. **版本号处理**：如"v1.2.3升级到v1.2.4"→"系统功能升级"
2. **代码量描述**：如"修改了200行代码"→描述实际功能改进
3. **技术栈更换**：如"从Vue2迁移到Vue3"→"页面架构升级，提升运行效率"
4. **性能指标**：保留具体数值，如"响应时间从3秒降至1秒"
5. **多人协作**：不区分个人贡献，统一描述团队成果
6. **多项目汇总**：❌ 禁止按项目分组或显示项目名称
   - 所有项目的提交记录完全合并，统一编号（1, 2, 3...）
   - 不添加"### XXX项目"这样的分组标题
   - 不在条目中体现"XXX项目中"或"在XXX项目"
   - 所有工作内容统一展示，按业务价值排序

## 示例转换

**原始记录**：
```
- 修复了用户登录API的token验证bug
- 重构前端组件库，提升代码复用性
- 优化MySQL查询语句，解决慢查询问题
```

**转换后**：
```
1. 修复用户登录验证异常，保障账户安全性
2. 优化页面功能模块结构，提高开发效率
3. 提升数据查询性能，解决系统响应缓慢问题
```

**原则**：领导无需了解技术实现细节，只需知道"做了什么业务功能、解决了什么业务问题"

## 执行提示
请严格按照上述规则处理输入内容，确保输出的周报内容专业、简洁、易于管理层理解。重点突出业务价值和实际效果，避免技术细节干扰。
